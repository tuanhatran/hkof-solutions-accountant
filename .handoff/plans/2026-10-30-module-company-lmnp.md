## 1. Context & Business Domain

In the French tax and real-estate domain:
- **LMNP (Loueur en Meublé Non Professionnel)**: A landlord (User A) owns/rents real estate and leases part of it (e.g. home office or professional premises) to a corporate entity (`Company ABC`). User A issues rent receipts (**Quittances de loyer**).
- **Company (Société - SAS/SARL/EURL)**: A company (User B) occupies space and reimburses the manager or pays office occupancy expenses (**Note de frais d'occupation**). Under French tax & URSSAF regulations, the rent receipt issued by the landlord is the mandatory accounting justification (**pièce justificative**) for the expense claim.
- **The Challenge**: Currently, data is strictly isolated per `user_id` (Tasks 74–78). If User A only has LMNP, and User B manages Company ABC, User A's lease cannot reference User B's company, and User B's expense statements cannot find User A's rent receipts. Furthermore, users currently see all menus regardless of their profile.

## 2. Architectural Answers to User Plan Questions

### Q1: How should we link Company ABC of User B with the lease of User A? Should we use a common company database?

**Analysis of a "Common Company Database":**
- Using a single, fully shared company table where any user can edit attributes is **insecure**: if User A edits Company ABC's address or manager name, it would alter User B's official tax filings and expense statements. Additionally, User B's company holds private data (pro-rata area calculations, active leases, internal employees, expense items).
- **Recommended Architectural Solution: "Managed Company" vs "Corporate Tenant Reference" via SIREN**:
  1. **Owner Authority**: User B remains the sole **owner & administrator** of `Company ABC` (identified by its 9-digit SIREN). User B configures expenses, surfaces, employees, and templates.
  2. **Cross-User Reference by SIREN**: When User A (LMNP) creates a commercial lease (`companyLease = true`), User A specifies the corporate tenant by **SIREN** (e.g. `123 456 789`).
  3. If Company ABC exists in the platform:
     - The lease stores `company_id = Company ABC.id`.
     - User A gains **read-only access to public legal identity fields** (Corporate Name, Legal Form, SIREN, Head Office Address, Manager Name) for printing on the rent receipt.
     - User A **cannot** alter Company ABC's settings, cannot see User B's expenses, and cannot delete the company.

---

### Q2: How do we link the rent receipt which is generated to be linked with Company ABC of User B?

**Recommended Architectural Solution: Dual-Read Access for Issuer & Tenant**:
1. When User A generates a rent receipt for a lease linked to Company ABC:
   - Stored row: `user_id = user_a.id` (User A is the issuer/creator) and `company_id = company_b.id` (Company ABC).
   - The PDF is generated and stored in storage.
2. In `RentReceiptRepository` / `RentReceiptService`:
   - Rent receipts are accessible if:
     - `receipt.user_id == currentUserId` (User A, the landlord / issuer), **OR**
     - `receipt.company_id IN (SELECT c.id FROM company c WHERE c.user_id == currentUserId)` (User B, the tenant company owner).
3. In `ExpenseStatementService`:
   - When User B opens `GenerateExpenseStatementPage` for Company ABC, `rentReceiptService.activeForLease(companyId, month, leaseId)` finds the active rent receipt generated by User A.
   - The rent amount is automatically populated into the statement.
   - When generating the statement export (PDF/ZIP), User A's rent receipt PDF is automatically bundled as the official justificatif.
4. In `HistoryPage`:
   - User A sees **"Quittances émises"** (issued receipts).
   - User B sees **"Quittances reçues (Société ABC)"** and expense statements.

## 3. Module & Admin Account Architecture

1. **Admin Account & Roles**:
   - `AppUser` receives a `role` (`ADMIN`, `USER`).
   - Default seed: `thtran@homeofficeexpenses.local` has `role = ADMIN`.
   - Admin has access to an administration interface (`/admin/utilisateurs`).
2. **User Modules**:
   - `AppUser` receives two flags:
     - `company_enabled` (boolean, default true)
     - `lmnp_enabled` (boolean, default true)
   - Admin can toggle these flags for any user via `PATCH /api/admin/users/{id}/modules`.
3. **Module Gating**:
   - **Backend**:
     - Endpoints under `/api/companies/**`, `/api/expense-statements/**`, `/api/expense-items/**` require `company_enabled == true` (returns 403 `MODULE_COMPANY_DISABLED` if inactive).
     - Endpoints under `/api/leases/**`, `/api/rent-receipts/**`, `/api/persons/**` require `lmnp_enabled == true` (returns 403 `MODULE_LMNP_DISABLED` if inactive).
   - **Frontend**:
     - `AppNav`: Shows/hides navigation items dynamically.
     - `router.tsx`: Gated routes redirect disabled modules to the user's active landing page.
     - `HistoryPage` & `TemplatesPage`: Filtered to show only document types relevant to the active module(s).
